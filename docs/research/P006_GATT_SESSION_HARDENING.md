# P006 GATT session hardening

`authorization: never_evaluated`

P005 rotated the ID immediately after Complete, Cancel, or a bad frame while retaining a response from the old ID. A subsequent challenge therefore described a different session from the result. P006 keeps one phase per BlueZ device path: `ChallengeIssued -> Receiving -> AwaitingCompletion -> ResponseAvailable -> Consumed`. Cancel and protocol errors transition to `ResponseAvailable`, discarding any assembler. Complete requires a fully assembled payload; its result carries that exact ID. An error response carries the ID of the server session that rejected the input, never an ID supplied by the offending frame. A client cannot read a new challenge while a result is available. Reading a short final response fragment consumes the result; when the length is an exact multiple of `MTU - 1`, the client must read once more at the end offset to receive the empty terminator and consume it; a later offset-zero challenge read creates a fresh ID and challenge and has no inherited result. A response expires 10 seconds after creation even if repeatedly read; any session expires after 30 seconds idle. Expiry discards state. There is no persistent replay ledger. A new challenge after expiry/reconnect is a new session, and old frames fail session checks.

A client must read a response sequentially from offset zero to its end. A short final fragment, including an empty read at the value length, consumes it; a full-size final fragment leaves it available for the ATT end-of-value read. A failed delivery or lost last response cannot be retried; reconnect and start again. An incomplete message expires 10 seconds after its last accepted frame, checked on the next frame or control command. A completed message awaiting Complete is subject to idle expiry. The ordered signal monitor invalidates the complete session on a BlueZ `Connected=false` or invalidation, even if reconnect follows before the next consistency poll. The synthetic ID and protocol are not authentication and cannot establish physical identity.

State is limited to 16 device paths, each at most 128 bytes; only an offset-zero challenge read allocates a session. A frame message is at most 1024 bytes, at most 256 ordered nonempty frames with sequence 0–255. ATT MTUs are 23–517, defaulting to 23 only when the option is absent; bad types and invalid values fail. Each assembler contains at most the bounded payload (plus bounded temporary copies); each result is at most 44 bytes, error 11. The fixed device limit bounds retained state, but zbus and BlueZ allocate a received D-Bus message before application validation; these limits are not a general local D-Bus denial-of-service defense. The server requires device paths and rejects malformed offsets, MTUs, write types, and prepared writes. A nonzero write offset and a write beyond MTU minus three fail. Read offsets are checked; a read returns at most MTU minus one. Partial result reads do not generate new state.

Registration uses random per-process object paths, a 2-second zbus method timeout, and the original BlueZ unique owner for manager calls. Advertisement cleanup is attempted before application cleanup. Registration flags distinguish acknowledged registration from an uncertain timed-out call; cleanup errors are included separately while preserving the original failure. A timed-out registration may have taken effect and is therefore subject to rollback. The private D-Bus connection closing removes exported objects; external BlueZ state after a lost bus or timed-out call is uncertain and cleanup failure is reported. The signal monitor detects BlueZ owner changes, device and adapter removal, and reported adapter power loss; polling remains a supplementary consistency check. The method timeout does not bound initial socket connection/handshake or prove behavior of a wedged kernel/daemon. Graceful signal and runtime handling remain explicit opt-in and bounded 1–300 seconds, subject to in-flight D-Bus timeouts and cleanup.

## Security assessment

| Risk | Actual mitigation / remaining limitation |
| --- | --- |
| Nearby malformed or resource-exhausting client | Bounded sessions, paths, messages, frame sequence, TTL and ATT checks; a client can still occupy a slot until expiry and radio/BlueZ resources remain outside these limits. |
| Session fixation, stale frames, cross-client leakage | Random IDs/challenges, per-device state, ID checks and the phase/result lifecycle; device paths are transport labels, not identities. Multiple clients and substitution are tested. |
| Fragmentation and cancellation races | Serialized state lock, ordered frames, bounded sizes, cancellation drops assembler; interrupted last response is intentionally non-retryable. |
| Disconnect/reconnect | Ordered BlueZ `Connected=false`/property-invalidated and device-removal signals discard that device's session, including partial data and unread ACKs. This depends on BlueZ emitting/delivering the event; actual controller behavior is NOT RUN. No authenticated reconnection guarantee. |
| BlueZ restart, D-Bus denial/loss, adapter disappearance | Unique-owner checks, bounded method calls, cleanup attempts and explicit errors. Restart/loss can prevent confirmation of cleanup. Permission denial is not hardware unsupported. |
| Relay, compromised host, RSSI, pairing | Unresolved: the transport provides no peer authentication, relay resistance, secure proximity or host integrity. Pairing, RSSI and connection never grant authorization. |

The P003/P004 mock enrollment keys and signed approvals are a separate simulation. A SHA-256 result is only a synthetic transport acknowledgment, not a Watch approval. No public key is learned or trusted, no Secure Enclave capability is asserted, and no PAM, polkit, login-manager or Linux unlock integration exists. GATT methods accept only the pinned BlueZ unique D-Bus owner; this is a local routing check, not authentication of the remote client or protection against a compromised host.

## P006A disconnect monitor and ordering

[BlueZ Device1](https://github.com/bluez/bluez/blob/master/doc/org.bluez.Device.rst) defines `Connected` as current connection state and says its changes emit `PropertiesChanged`. The [D-Bus Properties contract](https://dbus.freedesktop.org/doc/dbus-specification.html#standard-interfaces-properties) specifies `PropertiesChanged(interface, changed properties, invalidated names)`; the [ObjectManager contract](https://dbus.freedesktop.org/doc/dbus-specification.html#standard-interfaces-objectmanager) specifies `InterfacesRemoved(object path, interfaces)`. The bus daemon's `NameOwnerChanged` identifies a BlueZ restart or replacement. These signals describe local transport state, not authentication or proof of an active GATT session.

The server creates an unfiltered zbus 5.12 message stream on its *same* connection as the exported GATT server and installs bus match rules for the original BlueZ unique sender and selected adapter namespace, BlueZ's root `InterfacesRemoved`, and the bus daemon's `NameOwnerChanged(org.bluez)`. It rechecks the owner after installing rules, then queries a fresh ObjectManager snapshot addressed to that unique owner. No GATT object is exported before subscription. The stream is processed continuously, including during snapshot and registration. Matches are scoped to the process connection; no system configuration changes.

zbus documents that [receive positions](https://docs.rs/zbus/5.12.0/zbus/message/struct.Message.html#method.recv_position) are ordered only within a single connection; its [message stream](https://docs.rs/zbus/5.12.0/zbus/struct.MessageStream.html) must be continuously polled. Object-server method handlers may run concurrently, so a mutex around independent callbacks is not sufficient. The monitor processes the single stream in receive order: it applies each relevant signal, and on a GATT call it admits the matching sender/serial handler and waits for that handler to finish before processing the next message. Only the selected BlueZ owner can invoke the characteristic methods. Thus a disconnect signal *received by this connection before a GATT request* clears the old session before that request can execute; another device's session remains intact. A request ordered before the signal may finish, and an already delivered/in-flight response cannot be recalled. Ordering between messages received on different D-Bus connections is not inferred. A remote radio disconnect that BlueZ fails to report, or a signal BlueZ emits only after an already-accepted request, cannot be detected retroactively. Real BlueZ/hardware timing remains NOT RUN.

Subscription failure prevents startup. Owner change, adapter/manager removal, power loss or invalidated power state, malformed relevant signals, stream failure, a worker panic, or a one-second call-order watchdog closes the gate, clears sessions, and stops the server with cleanup; there is no polling-only fallback. A fresh process can establish new subscriptions and sessions after a failure. Polling retains its one-second role as a supplementary consistency check. A bounded stream and watchdog can cause a denial of service under load, and neither the one-second watchdog nor zbus method timeout bounds initial D-Bus connection/handshake or a wedged OS.
