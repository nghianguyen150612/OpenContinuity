# P003 transport matrix

Evidence snapshot: 2026-10-28. **DOCUMENTED** means Apple documents an API or behavior; it does not mean OpenContinuity implemented it or validated it on Apple Watch SE 2. All physical tests below are **NOT RUN**.

| Candidate | Endpoint roles and public API | Availability / runtime behavior | Security and delivery limits | P003 decision |
| --- | --- | --- | --- | --- |
| Direct BLE, foreground | Linux BlueZ advertises a GATT service; Watch app is a `CBCentralManager` central and connects to a peripheral. Core Bluetooth is available to Watch apps; Apple has a Watch-specific CoreBluetooth session. | User launches/opens Watch app; Bluetooth authorization and a Watch-capable Xcode target required. Linux controller and BlueZ GATT implementation are not in this repository. SE 2 lists Bluetooth 5.3. | Pairing/link encryption is transport protection, not Linux account binding. App identity must be enrolled and every approval signed over a fresh challenge. RSSI is not proximity proof. | **CONDITIONAL GO** for a foreground hardware experiment. No production radio adapter. |
| Direct BLE, Watch as peripheral | Linux scans and connects to a Watch-hosted GATT service. | `CBPeripheralManager` cannot advertise services on watchOS per its current Apple documentation. | No service advertisement means Linux has no public third-party Watch peripheral endpoint to discover with this API. | **BLOCKED** for this topology. |
| Direct BLE, Watch background central | Existing BLE connection/reconnect and incoming accessory data during approved background task modes. | Apple documents background refresh reconnection (watchOS 8+) and retained peripheral connections while suspended (watchOS 9+). Task types and runtime are scheduled/constrained. | Does not guarantee launch on arbitrary Linux challenge or continuous listener time. Device can be locked, app terminated, radio unavailable, user can disable refresh, or task can be delayed. | **NO-GO** for unattended/continuous authorization; test limited wake scenarios only. |
| Direct IP / LAN | watchOS `URLSession` may use connected iPhone, known Wi-Fi or cellular. Candidate is a request to a configured Linux host endpoint. | watchOS constrains low-level networking; Apple directs apps to URLSession for URL requests. Local-network privacy table says no watchOS local network privilege flow. `URLSession` local host behavior is not validated. | Routing may traverse iPhone or cellular; endpoint reachability and route do not prove peer identity or presence. Need TLS/pinned enrollment identity or application signature, bounded timeouts, and host firewall exposure review. | **UNKNOWN**; no Linux listener or physical test. |
| Watch ↔ iPhone via WatchConnectivity | Paired WatchKit and iOS apps use `WCSession`. | `sendMessage` requires current reachability and active session; Watch app foreground can wake its iOS app, but iPhone-to-Watch immediate send does not wake the Watch extension. Queued transfers are eventual, not prompt. | Paired app identity/phone ownership are not Watch cryptographic proof. Compromised relay can drop, delay, replay or route traffic. It cannot forge a Watch key signature if Linux validates it directly. | **GO** as optional foreground relay; not a presence or identity substitute. |
| iPhone ↔ Linux over BLE | iOS CoreBluetooth central/peripheral connection to a Linux BlueZ endpoint. | iOS role, permissions, background modes and task scheduling need implementation-specific tests; no iOS target exists here. | BLE bond alone does not authorize. Phone can transport only opaque Watch-signed messages; phone key must not issue approval. | **HYPOTHESIS / unimplemented**, needs iOS/BlueZ test. |
| iPhone ↔ Linux over LAN | iOS networking to a host local-IP service, with user permission and local-network Info.plist description as applicable. | iOS 14+ local network privacy requires purpose declaration and permission for LAN operations; app execution still varies in background. | Authenticated TLS and Watch signature required. Local LAN may be unavailable/isolated; no internet fallback or phone approval fallback may silently substitute identity. | **HYPOTHESIS / unimplemented**, needs iOS/host test. |

## Relay timing and failures

Use an interactive `WCSession.sendMessage` only while `isReachable` is true. Treat error, session deactivation, iPhone absent, Watch app not running, or timeout as denial. Do not fall back to queued `transferUserInfo` for a current login challenge: its delivery is eventual and order does not create a deadline. A user may open the Watch app to initiate the request. Bound all challenge lifetimes and never extend them because a message was delayed.

## Wormhole and transport binding

A BLE relay, IP forwarder or compromised iPhone can tunnel a valid Watch exchange from a distant endpoint. Ordinary BLE RSSI and connection latency cannot establish distance. P003 has no secure distance-bounding evidence for Linux ↔ SE 2. Therefore a signed explicit confirmation can establish intent and key possession but does **not** prove physical proximity to the Linux host. Any future use must disclose and accept that residual risk or obtain an independently validated anti-relay mechanism before unlock consideration.
